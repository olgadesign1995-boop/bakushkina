# Промпт-инструкция: публикация сайта через GitHub → Vercel и победа над 404

Универсальный сценарий для агента. Ничего проектного здесь нет — файл можно
приложить к любой новой задаче вместе с основным плейбуком.

---

## Промпт для агента (скопировать и вставить)

> Опубликуй проект по схеме GitHub → Vercel и доведи до рабочего адреса
> `*.vercel.app`. Требования:
>
> 1. Работай через API обоих сервисов, а не через инструкции мне. Если нет
>    доступа — сразу первой строкой скажи, какие токены нужны и где их взять.
>    Не используй одноразовые device-коды: они живут 10–15 минут и умирают
>    в паузе между сообщениями.
> 2. Если сайт отдаёт 404 — не гадай. Сначала сними заголовки ответа,
>    проверь настройки проекта через API и назови точную причину, потом чини.
> 3. Настрой процесс так, чтобы твои правки уезжали в отдельную ветку и
>    появлялись как **Preview**-деплой, а я подтверждала выкатку кнопкой
>    **Promote to Production**. В production-ветку напрямую не пушь.
> 4. После каждой правки: `lint`, `build`, push, короткий отчёт с точным
>    названием ветки и хешем коммита, который нужно промоутить.
> 5. Секреты — только в Environment Variables. В код и репозиторий — никогда.

## Часть 1. Диагностика 404: три шага вместо догадок

### Шаг 1. Снять заголовки ответа

```bash
curl -s -I https://<адрес>/ | grep -iE "x-vercel-error|x-vercel-id|server"
```

Читать нужно поле `x-vercel-error`:

| Значение | Что означает | Куда копать |
|---|---|---|
| `DEPLOYMENT_NOT_FOUND` | деплоя вообще нет | проект не создан или адрес чужой |
| `NOT_FOUND` | деплой есть, но внутри пусто | **сборка не выполнялась** — см. шаг 3 |
| нет заголовка, отдаётся HTML 404 | приложение работает | ошибка в роутинге самого приложения |

### Шаг 2. Проверить, чей это ответ

Если в заголовках видны кастомные значения из конфига проекта
(`x-frame-options`, `permissions-policy` и т. п.) — платформа **читает
репозиторий**, конфиг применяется. Значит код и подключение в порядке,
а проблема в настройках сборки. Это сужает поиск сразу.

### Шаг 3. Проверить все пути, а не только главную

```bash
for p in / /robots.txt /sitemap.xml /favicon.ico; do
  printf "%-20s" "$p"; curl -s -o /dev/null -w "%{http_code}\n" "https://<адрес>$p"
done
```

**Ключевой признак:** если 404 отдают *абсолютно все* пути, включая статику, —
дело не в роутинге приложения. Сборка не запускалась вовсе.

### Шаг 4. Сверить с локальной сборкой

```bash
npm run build && npm run start -- --hostname 0.0.0.0
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/
```

Локально `200`, на хостинге `404` → **код исправен, виновата конфигурация проекта.**

## Часть 2. Главная причина 404 — не тот Framework Preset

Самая частая и самая незаметная поломка.

```bash
curl -s -H "Authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v9/projects?limit=50" \
| python3 -c "
import json,sys
for p in json.load(sys.stdin)['projects']:
    print(p['name'], '| framework:', p.get('framework'),
          '| root:', repr(p.get('rootDirectory')),
          '| build:', repr(p.get('buildCommand')))"
```

Если в ответе `framework: None` — диагноз поставлен. Платформа считает проект
набором статических файлов, **не выполняет команду сборки** и раздаёт пустой
каталог. При этом деплой честно показывает статус `Ready`, а заголовки из
конфига применяются — отсюда ощущение, что «всё собралось, но сайта нет».

### Лечение — один запрос

```bash
curl -s -X PATCH -H "Authorization: Bearer $VERCEL_TOKEN" \
  -H "Content-Type: application/json" \
  "https://api.vercel.com/v9/projects/<projectId>" \
  -d '{"framework":"nextjs","rootDirectory":null,
       "buildCommand":null,"outputDirectory":null,"installCommand":null}'
```

`null` в командах означает «использовать значения по умолчанию для фреймворка» —
это правильнее, чем прописывать их руками.

Через интерфейс: **Settings → Build and Deployment → Framework Settings →
Framework Preset**, все Override — выключить.

### Другие причины 404, по убыванию частоты

| Причина | Как распознать | Решение |
|---|---|---|
| Пустой репозиторий | в репозитории 1–2 файла | залить код |
| Не тот репозиторий | проект смотрит на другой репо | сверить `link.repo` в API |
| `Root Directory` указывает в подпапку | сборка ищет `package.json` не там | очистить поле |
| Смотрят не на тот адрес | у проекта несколько доменов | взять из API список алиасов |
| Проверка сразу после push | сборка идёт 1–2 минуты | дождаться статуса `READY` |

**Отдельная ловушка:** у проекта может быть несколько адресов, и рабочий —
не тот, что кажется очевидным. Правильный список берётся так:

```bash
curl -s -H "Authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v9/projects/<projectId>/domains" \
| python3 -c "
import json,sys
for d in json.load(sys.stdin)['domains']: print(d['name'], d.get('verified'))"
```

## Часть 3. Доступы: только постоянные токены

Одноразовые device-коды в такой работе не годятся — короткий срок жизни,
и они истекают, пока идёт переписка. Нужны два постоянных токена.

**GitHub:** Settings → Developer settings → Personal access tokens (classic) →
Generate new token → область **`repo`** → срок 90 дней.

**Vercel:** Account Settings → Tokens → Create Token → выбрать нужный scope
(личный аккаунт или команда) → срок по желанию.

### Правило передачи

Токены передаются **файлом-вложением**, не текстом в чате: сообщения остаются
в истории, и такой токен считается скомпрометированным.

```
GITHUB_TOKEN=...
VERCEL_TOKEN=...
```

Агент обязан: положить файл в служебный каталог, внести каталог в `.gitignore`,
удалить исходное вложение, проверить оба доступа и подтвердить результат.
После публикации — напомнить об отзыве токенов.

### Проверка, что доступ живой

```bash
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" https://api.github.com/user
curl -s -H "Authorization: Bearer $VERCEL_TOKEN" https://api.vercel.com/v9/projects?limit=1
```

Токен Vercel, выданный на команду, может отвечать `not_found` на
`/v2/user` — это нормально. Проверять его нужно на `/v9/projects`.

## Часть 4. Формат публикации: Preview → Promote to Production

Цель: правки видны заранее, а на боевой сайт попадают только по кнопке.

### Настройка

1. Production Branch проекта — основная ветка (обычно `main`).
2. Агент работает в отдельной ветке (`dev` или ветка сессии) и пушит **только** в неё.
3. Любой push в неветку-production даёт **Preview**-деплой со своим адресом.

### Рабочий цикл

```
агент: правка → lint → build → commit → push в dev
   ↓
Vercel: Preview-деплой, статус Ready
   ↓
человек: открыть Preview, посмотреть
   ↓
устраивает → Deployments → ⋯ → Promote to Production
не устраивает → ничего не нажимать, боевой сайт не изменился
```

Кнопка **Promote to Production** живёт в меню `⋯` справа в строке деплоя.
Она не пересобирает проект, а переиспользует готовую сборку — выкатка мгновенная.

### Каноничный деплой-блок в отчёте агента

После каждой правки агент присылает ровно такую таблицу:

| Параметр | Значение |
|---|---|
| Ветка | `dev` |
| Коммит для промоута | `<короткий хеш>` — «<сообщение коммита>» |
| `lint` | ✅ / ошибки |
| `build` | ✅ / ошибки |
| Где смотреть | Preview-адрес деплоя |

Без хеша и названия ветки отчёт бесполезен: в списке деплоев несколько
похожих строк, и промоутить придётся наугад.

## Часть 5. Переменные окружения — где теряется время

1. **Две галочки, а не одна.** Переменную нужно отмечать и для **Production**,
   и для **Preview**. Если поставить только Production — Preview-деплои
   (те самые, что подтверждаются кнопкой) окажутся без значений, и поведение
   будет отличаться от боевого.
2. **Redeploy обязателен.** Значения вшиваются в момент сборки. Изменили
   переменную — пересоберите, иначе ничего не поменяется.
3. **Публичные и серверные.** Переменные с префиксом `NEXT_PUBLIC_` попадают
   в браузер — туда нельзя класть ничего секретного. Ключи и токены остаются
   серверными.
4. **Проверять снятием кеша.** При повторной сборке снимайте галочку
   «Use existing Build Cache», иначе можно получить старый результат.

Типовой набор для лендинга: публичный адрес сайта (снимает `noindex`
и чинит OG-разметку с картой сайта) плюс ключи канала приёма заявок.

## Часть 6. Чек-лист приёмки после публикации

```bash
for p in / /robots.txt /sitemap.xml /favicon.ico; do
  printf "%-20s" "$p"; curl -s -o /dev/null -w "%{http_code}\n" "https://<адрес>$p"
done
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"name":"Тест","contact":"test@example.com","message":"проверка"}' \
  -o /dev/null -w "форма: %{http_code}\n" "https://<адрес>/api/<endpoint>"
```

- [ ] Главная отдаёт `200`, размер ответа похож на реальную страницу
- [ ] Заголовок первого уровня на месте (проверить `grep` по ответу, а не глазами)
- [ ] Служебные файлы отдаются: карта сайта, robots, иконка, OG-картинка
- [ ] Медиафайлы отдаются (проверить хотя бы один путь из каждой папки)
- [ ] Форма без настроенных ключей возвращает честную ошибку, а не ложный успех
- [ ] `robots.txt` соответствует замыслу: закрыт до готовности, открыт после
- [ ] В репозитории нет секретов: `git ls-files | grep -i secret` пусто

## Часть 7. Устойчивость рабочего окружения

Если рабочая среда очищается между сессиями (пропадают история git, зависимости,
сгенерированные файлы) — репозиторий становится главной страховкой.

Восстановление вместо долгой пересборки:

```bash
git init -q -b main
git remote add origin <адрес репозитория>
git fetch -q origin main && git reset -q --hard FETCH_HEAD
npm install
```

Правила, которые экономят часы:

- Производные файлы (обработанные изображения) **держать в репозитории**, а не
  генерировать заново: пересборка занимает минуты, выгрузка из репозитория — секунды.
- Тяжёлые исходники — наоборот, в `.gitignore`.
- Перед любой операцией с git проверять, что каталог `.git` вообще существует.
- Не доверять цепочкам через `&&` — проверять код возврата отдельно.
- Служебные каталоги окружения не должны попадать в `git add -A`: они раздувают
  репозиторий. Контролировать через `git count-objects -vH`.

## Краткая формула

**404 при статусе Ready = сборка не выполнялась.** В девяти случаях из десяти
причина в том, что платформа не распознала фреймворк. Проверяется одним
запросом к API, чинится одним PATCH-запросом. Всё остальное — следствие.
